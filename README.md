# KegTrace · 精酿酒吧空桶回收押金与批次追溯平台

## 原始需求

> 建设精酿酒吧空桶回收押金与批次追溯平台，可采用 React、Go 和 PostgreSQL。酒厂向合作酒吧发出不同批次的 IPA、世涛、小麦和酸啤时，平台记录酒桶编号、容量、酒液批次、灌装日期、最佳饮用期、押金金额、配送司机和酒吧收货人。酒吧开桶后可以反馈出酒速度、气压问题、口味异常和客诉；酒桶打空后，酒吧预约回收，司机扫码确认空桶数量、外观、残液和封盖状态。若酒吧延迟归还、酒桶丢失、桶体变形、批次口味被多家投诉、司机漏扫或清洗厂检测不合格，平台要把酒厂仓库、酒吧店长、司机、清洗厂、品控和财务放在同一只桶或同一批酒中处理。押金释放、扣款、再灌装资格和批次停售建议都基于这些记录生成。平台还要支持多城市经销商、酒桶押金账期、节日临时铺货和批次召回通知。酒厂需要按桶看到它在哪家酒吧、是否开桶、是否回收、是否清洗合格，财务需要按桶释放或扣减押金。批次召回时还要区分已售卖、已开桶和未开桶库存。如果某个批次暂停销售，平台还要通知已收货酒吧、待配送订单和经销商库存，避免继续开桶售卖。

## 本期需求：口味异常批次排查

> 多家酒吧反馈同一批 IPA 有氧化味时，平台关联灌装时间、运输温度、酒吧开桶日期、出酒设备和客诉照片。品控确认前，该批次剩余酒桶进入暂停配送状态。暂停配送期间，销售人员能看到受影响酒吧和可替换批次，品控结论会决定已开桶酒是否需要召回或折价。召回决定会同步销售和仓库备货。

实现要点：

- **自动排查**：同一批次被 ≥2 家酒吧反馈口味异常/客诉时，自动生成「口味异常排查单」（也可由品控/仓库手动建立），同时生成批次口味投诉工单。
- **证据关联**：排查详情页一屏关联批次灌装时间、含该批次酒桶配送单的运输温度（冷链记录，超温高亮）、各酒吧开桶日期、客诉反馈中的出酒设备与客诉照片（反馈表单支持上传 ≤3 张、单张 ≤400KB 的照片）。
- **暂停配送**：排查单建立即置批次 `delivery_hold`，该批次禁止出库/新灌/再灌装，含该批次的待配送/配送中订单自动暂缓；品控确认前酒吧仍可正常售卖。
- **销售视角**：新增「销售」角色，暂停配送期间可在排查详情看到受影响酒吧（在店/已开桶/已打空桶数）与同酒款可替换批次（在售、未暂停、在库可发桶数）。
- **品控结论**三选一：**召回**（复用批次召回，拆分已售/已开桶/未开桶并通知）、**折价**（已开桶按折价比例结算，批次停售，通知酒吧/经销商/财务）、**排除异常**（解除暂停配送，暂缓订单恢复待配送）。召回与折价结论都会同步通知销售与仓库备货。

## 技术栈与架构

- **前端**：React 18 + Vite + React Router（构建产物由 Go 服务静态托管，单端口交付）
- **后端**：Go 1.22（标准库 `net/http` + `lib/pq`），REST API，Bearer Token 会话，逐接口角色鉴权
- **数据库**：PostgreSQL 16（仅 compose 内部网络，不发布宿主端口）
- **部署**：多阶段 Dockerfile（非 root 用户 + HEALTHCHECK），`docker compose` 一键启动

```
┌────────────┐      ┌─────────────────────┐      ┌────────────┐
│  浏览器     │ ───▶ │  app (Go + React)   │ ───▶ │  postgres  │
│            │ :8080│  /api/* + 静态站点   │ 5432 │  (内部网络) │
└────────────┘      └─────────────────────┘      └────────────┘
```

## 快速启动（验证方式 = 宿主 docker compose up）

```bash
cp .env.example .env        # 按需修改 CC_PUBLISH_PORT 等
docker compose up -d --build
docker compose ps           # app 健康检查通过后
docker compose port app 8080   # 查看实际映射端口（如 0.0.0.0:3222）
# 浏览器访问 http://localhost:<端口>
# 结束验证后释放资源：
docker compose down
```

- 应用容器内部固定监听 `8080`，仅应用端口通过 `${CC_PUBLISH_PORT}` 发布到宿主；数据库不发布端口，应用通过服务名 `db` 访问。
- 首次启动自动建表并写入演示数据（批次 / 酒桶 / 在途配送单 / 投诉工单 / 押金流水等）。

## 演示数据与关键业务流

种子数据包含：3 个城市经销商、4 家酒吧、5 个批次（IPA/世涛/小麦/酸啤 + 一个 7 月老批次）、21 只酒桶（在库/配送中/在店/已开桶/已打空/待清洗/待再灌装/清洗不合格各状态）、1 个已签收配送单（运输温度 12.5℃，冷链超温伏笔）、1 个配送中单（4.0℃）、1 个中秋节日临时铺货待配送单、酸啤批次已被 2 家酒吧投诉（已生成品控工单 + 排查单 INV000001，批次已暂停配送）、IPA-20260901 已被野鹅酒吧反馈 1 次氧化味（再有一家投诉即自动触发排查）、1 只逾期 54 天未归还酒桶（已生成逾期工单）、1 笔待释放押金。

推荐体验路径：

1. **仓库** `warehouse`：批次管理新建批次 → 酒桶追溯登记酒桶 → 配送订单新建配送单（勾选在库酒桶，可选"节日临时铺货"、登记运输温度）。
2. **司机** `driver1`：配送订单"开始配送 → 送达"（送达时可登记实际运输温度）。
3. **店长** `bar1`：配送订单"签收"（填收货人，自动按桶收取押金）→ 酒吧操作台"开桶 → 反馈（勾选口味异常+客诉，选择出酒设备、上传客诉照片）→ 打空" → 勾选空桶"预约回收"。
4. **口味异常排查（本期）**：`bar1` 已对 IPA-20260901 反馈过氧化味；再用 `bar2` 对 KEG-1009 提交"口味异常+客诉"反馈 → 达到两店投诉，自动生成排查单 INV000002 且批次立即暂停配送（批次管理可见"暂停配送"标记，该批次禁止出库/灌装，在途订单自动暂缓）。
5. **销售** `sales`：口味排查 → 打开 INV000002 → 查看关联证据（灌装时间、配送单 12.5℃ 超温、两店开桶日期、出酒设备、客诉照片）与"受影响酒吧""可替换批次（IPA-20260715）"。
6. **品控** `qc`：口味排查 → INV000002 → 提交结论：选"召回"则批次召回并拆分已售/已开桶/未开桶，同步通知销售与仓库备货；选"折价"需填折价比例，批次停售并通知酒吧/经销商/财务；选"排除异常"则解除暂停配送、暂缓订单恢复待配送。也可对种子排查单 INV000001（酸啤）直接给结论。
7. **司机** `driver1`：回收预约 → 详情逐只扫码（外观/残液/封盖）→ 完成回收；少扫会生成"司机漏扫"工单；外观选"变形/破损"自动生成桶体异常工单并取消再灌装资格。
8. **清洗厂** `washer`：清洗检测登记。合格 → 酒桶"待再灌装"且自动生成"押金待释放"（通知财务）；不合格 → 生成工单、取消再灌装资格。
9. **财务** `finance`：押金台账按账期查看收取/释放/扣减，对待结算记录点"结算"；酒桶详情页可直接"押金扣减"；可手动"扫描逾期未归还"。
10. **品控** `qc`：批次详情"暂停销售"（通知已收货酒吧、暂缓待配送/配送中订单、通知经销商，且该批次禁止开桶/出库）；"发起召回"返回并通知**已售卖 / 已开桶 / 未开桶**三类库存拆分。
11. **协同工单**：六类异常（延迟归还/丢失/变形/批次投诉/漏扫/清洗不合格）在同一工单中留言协同，仓库/品控/财务可结案并附带押金扣款。

## 本地开发

```bash
# 后端（需 Go 1.22+ 与本地 PostgreSQL，DATABASE_URL 指向数据库）
cd backend && DATABASE_URL="postgres://keg:kegpass@localhost:5432/kegdb?sslmode=disable" \
  PORT=8080 STATIC_DIR=../frontend/dist go run .

# 前端（另开终端，Vite 开发服务器，代理 /api 到 8080）
cd frontend && npm ci && npm run dev

# 生产形态：前端构建后由 Go 静态托管
cd frontend && npm run build
```

## 目录结构

```

├── .env.example            # CC_PUBLISH_PORT / 数据库账号等

```

## 说明

- 密码使用加盐 SHA-256 哈希（演示用途；生产应替换为 bcrypt/argon2）。
- 会话保存在应用内存中，重启后需重新登录。
- 逾期判定：酒桶到店超过 30 天未归还（服务启动、回收完成、手动扫描时触发检查）。
